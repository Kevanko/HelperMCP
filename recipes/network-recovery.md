# Сценарии сети с независимым восстановлением Windows

Используй `net_check` для диагностики и `net_recover` для изменений, способных
оборвать удалённый доступ. Подготовленные шаги исполняются локально в отдельном
процессе даже без relay. Произвольные команды по-прежнему доступны через `run` и
`start_process`, но сетевые изменения выполняй через описанные здесь сценарии:
у обычного shell-скрипта нет автоматического отката.

## Как устроена защита

Перед первым изменением сохраняются точные значения и идентичность ресурсов.
Helper создаёт задание Windows от SYSTEM, проверяет его реальным запуском без
изменений, читает настройку задания обратно и только затем запускает исполнитель.
Задание запускает откат по сроку, при следующей загрузке и повторяет попытку после
ошибки. Запись undo сохраняется **до** каждого изменения. Закрытие Helper или
потеря relay не отменяют откат. Фоновый исполнитель сам восстанавливает настройки
после завершения сценария, не ожидая срока аварийного задания.

Файлы лежат в `%ProgramData%\HelperMCP-NetworkRecovery`, вне репозитория.
SYSTEM и повышенные Administrators имеют право записи, пользователь — чтение.
Нельзя удалять каталог активного задания. Для очистки законченных заданий сначала
проверь `status`: незавершённый/неудачный откат требует восстановления.

Нужен Helper с правами администратора. Обычный Helper вернёт ошибку **до** изменений;
`util {op:"elevate"}` показывает штатный UAC. Это не абсолютная гарантия: выключенный
ПК, поломка драйвера, физический обрыв линии или недоступность всех адресов relay
могут помешать восстановлению. Не проверяй отключение сети на компьютере оператора
во время его текущей работы ради тестирования программы.

## Команды

Добавляй `session` при использовании общего MCP endpoint.

```json
{"op":"templates"}
{"op":"list"}
{"op":"status","job":"ИДЕНТИФИКАТОР_ИЗ_START"}
{"op":"rollback","job":"ИДЕНТИФИКАТОР_ИЗ_START"}
```

Примеры для `net_recover`; индекс 14 и названия служб обязательно замени
значениями проверяемого компьютера. Автоматически выбирать все адаптеры запрещено.

```json
{"op":"start","template":"guard-selftest","interface_index":14}
{"op":"start","template":"adapter-cycle","interface_index":14,"seconds":3}
{"op":"start","template":"disconnect","interface_indices":[14,17],"seconds":10,"rollback_after_s":90}
{"op":"start","template":"zapret-ab","service":"zapret","interface_index":14,"url":"https://discord.com/"}
{"op":"start","template":"warp-cycle","service":"CloudflareWARP","interface_index":14}
{"op":"start","template":"fake-dns","interface_index":14,"servers":["1.1.1.1","8.8.8.8"],"allow_commit":true}
{"op":"start","template":"stale-route","interface_index":14,"destination":"198.18.0.0/24","gateway":"192.168.0.1","allow_commit":true}
{"op":"start","template":"mtu-trial","interface_index":14,"mtu":1400}
```

Первый запуск на новом компьютере начни с `guard-selftest`: он проверяет SYSTEM
preflight, фоновый исполнитель и контрольный запрос, не меняя сетевых настроек.
`status=rolled_back` с сохранённым probe подтверждает завершение этого теста;
он не заменяет проверку реального отключения/включения адаптера.

`disconnect` отключает **только явно перечисленные** включённые адаптеры, ждёт,
включает их обратно и делает контрольный запрос. Если перечислены все пути к
интернету, связь действительно временно пропадёт. Проверять это на чужом ПК
можно в рамках порученного ремонта, после успешного запуска защиты.

`zapret-ab` измеряет до остановки службы, после остановки и после её восстановления.
Остановка службы не доказывает выгрузку всех WinDivert/WFP-фильтров. `warp-cycle`
не сбрасывает регистрацию WARP и не меняет организационные политики.

`fake-dns` сохраняет исходный список **статических** IPv4 DNS, а при его отсутствии
возвращает DHCP DNS; IPv6 DNS не меняется. `stale-route` выбирает одну точную запись
ActiveStore, исключает DHCP/kernel и PersistentStore. Удаление всего диапазона
fake-IP или таблицы маршрутов недопустимо. `mtu-trial` меняет только IPv4 MTU
ActiveStore указанного интерфейса и возвращает исходное значение.

Без `allow_commit:true` изменения всегда отменяются. При нём остаётся срок
45–300 секунд для проверки. После повторной диагностики и проверки нужного
приложения вызови `commit`. Helper дополнительно проверит авторизованный обмен
с relay. После истечения срока commit запрещён. Одного HTTP 200 недостаточно,
чтобы считать VPN/игру исправленными. Отключение адаптеров закрепить нельзя.

## Собственный фоновый сценарий

```json
{"op":"start","rollback_after_s":120,"steps":[
  {"op":"probe","interface_index":14,"url":"https://www.microsoft.com/"},
  {"op":"service_stop","name":"zapret"},
  {"op":"wait","seconds":3},
  {"op":"probe","interface_index":14,"url":"https://www.microsoft.com/"},
  {"op":"restore"},
  {"op":"wait","seconds":5},
  {"op":"probe","interface_index":14,"url":"https://www.microsoft.com/"}
]}
```

До 12 шагов. `restore` возвращает предыдущие изменения и позволяет продолжить
сценарий. `probe` записывает DNS/TCP/TLS/HTTP-результаты локально; они доступны в
`status.probes` после возврата связи. У probe тот же предел: HTTP-доступ не равен
протокольной проверке VPN. При ошибке применения дальнейшие шаги прекращаются,
исполняется откат; неудачные undo остаются для следующей попытки SYSTEM.

Для операций, которым нет готового шага, можно передать `script` с двумя локальными
файлами `.ps1`: действием и явным откатом. Сначала прочитай оба файла, проверь
синтаксис и обратимость; затем передай `script_rollback_reviewed:true`:

```json
{"op":"start","rollback_after_s":120,"script_rollback_reviewed":true,"steps":[
  {"op":"script","apply_path":"C:\\Repair\\apply.ps1","undo_path":"C:\\Repair\\undo.ps1","timeout_s":10},
  {"op":"probe","interface_index":14,"url":"https://www.microsoft.com/"}
]}
```

До запуска фиксируются копии файлов с SHA256, UTF-8 BOM и проверкой PowerShell
parser. Изменение исходного файла после подготовки не меняет выполняемый сценарий.
Таймаут шага 2–20 секунд, stdout/stderr сценария не передаются в отчёт. При таймауте
останавливается дерево запущенного шага, после чего вызывается undo. Скрипты не
должны создавать отделённые процессы/задачи и не должны зависеть от рабочего
каталога, интерактивного профиля или подключённых дисков пользователя: аварийный
откат исполняется от SYSTEM. Делай undo идемпотентным и сохраняй исходные значения
внутри подготовленного сценария. Helper не умеет автоматически вывести обратную
операцию для произвольного shell-кода; флаг проверки — ответственность агента,
а не доказательство корректности написанного undo.

## Разбор распространённых проблем

Эти случаи собраны по документации и сообщениям пользователей. Сообщение на
форуме — основание для гипотезы, не доказательство причины на текущем ПК.

| Симптом | Что проверить | Следующий шаг |
|---|---|---|
| После закрытия VPN нет сайтов | `net_check mode=routes`, DNS физического адаптера, наличие локального резолвера | Проверить UDP DNS на том же адаптере; при подтверждённом оставшемся fake-IP — `fake-dns` с откатом |
| Интернет умирает при zapret + TUN | Состояние winws/WinDivert, route/DNS, контрольный адрес напрямую и через TUN | `zapret-ab` на одном текущем профиле; не включать второй VPN ради сравнения |
| WARP вместе с VPN ломает DNS | Кто управляет DNS, default/split routes и firewall | Разделить DNS и маршрутизацию по документации именно установленной версии; `warp-cycle` — только диагностический перезапуск |
| DNS отвечает, TUN не передаёт данные | Остаточные маршруты к `198.18/15`, особенно более узкие через LAN gateway | Проверить владельца записи; `stale-route` только для одной доказанно лишней ручной непостоянной записи |
| В исключениях клиента записан relay, но Helper offline | Фактический Get-NetRoute и путь сокета, а не только UI настроек | Исправить настройку владельца маршрутов; собственный транспорт Helper выбирает проверенный путь независимо от этого списка |
| TUN работает, альтернативный DNS недоступен | Windows strict-route/WFP, DNS mode и используемый интерфейс | Не объявлять провайдера виноватым по отказу UDP53: strict-route может намеренно блокировать DNS вне туннеля |
| Ping 89, при загрузке 5000 | Idle/load TCP/TLS/TTFB, реально скачанные байты и overlapping samples, CPU/RAM | Отделить перегрузку канала от локального CPU и сервера; небольшой тест не доказывает bufferbloat |
| Мелкие запросы идут, видео/большие ответы зависают | Размеры загрузок, retransmission/MTU, транспорт QUIC против TCP | `mtu-trial` на одном интерфейсе и сопоставимые повторные замеры; не ставить универсальное MTU всем |
| В клиенте все серверы красные, выбранный работает | URL проверки задержки, DNS, журналы ядра, реальный запрос через выбранный proxy | Не приравнивать индикатор к проверке всех транспортов; REALITY/UDP требуют совместимого ядра |
| Discord открывается, голос не работает | HTTPS отдельно от UDP/voice, DNS и правила конкретного клиента | Проверять реальный голосовой транспорт; HTTP 200 Discord не подтверждает голос |
| После удаления zapret остаётся WinDivert | Win32_SystemDriver, State, службы и их владельцы | Не удалять драйверы общим `sc delete`: они могут быть нужны другим приложениям |
| WARP завис в Connecting и пропала связь | Статус/журналы клиента, доступность orchestration API и ingress отдельно, протокол MASQUE/WireGuard и WFP | Запускать пробное подключение с заранее подготовленным отключением; один открытый TCP-порт не подтверждает туннель. Требуемые адреса зависят от версии и типа регистрации |

Для стенда в ВМ различай проверку восстановления служб и проверку обхода DPI.
Сеть NAT за VPN/fake-IP хоста не воспроизводит прямой доступ провайдера. Автор
zapret рекомендует bridge для blockcheck в ВМ; не перестраивай сеть хоста ради
автоматической проверки. По умолчанию winws исключает LAN (`--wf-filter-lan=1`):
HTTP к локальному стенду при запущенной службе ещё не доказывает перехват пакетов.
Узкий лабораторный фильтр должен явно включать свой адрес/порт, а обработку
нужно подтвердить журналом. Не переносить лабораторные параметры всем пользователям.
